# LX relayout — second review pass

Reviews `c60f5d81` ("Harden LX relayout ownership and validation") against `67df28b`,
the state covered by `LX_RELAYOUT_MERGE_CHECKLIST.md`. Delta report: it assumes that
checklist has been read, and reports only what changed.

Headline: six of the seven blocking items are closed. The one that mattered most turned
out to be **B6**, the sub-dimension endianness inversion — which the first pass could
only mark "unknown" — while **B1**, which the first pass called the headline blocker,
re-scores to open-but-unproven: no pass could construct a wrong-numbers case for it.

Four regressions came in with the hardening commit; two are worth fixing before merge.

## Regressions introduced by the hardening commit

Four, none of them a demonstrated wrong-numbers path. Two are worth fixing before merge.

**1. The matmul/weight gate uses `break`, so one weight-fed matmul discards every sibling plan for that source.** `lx_relayout.py:288-296`, with the loop's `else: result.extend(source_plans)` at `:330-331`. `_is_activation_source(operations, producer)` is a property of the **producer** â loop-invariant â but it is evaluated inside the per-consumer loop, and its failure path is `break`, which throws away every plan already accumulated. Concrete: `w = restickify(<graph input>)` consumed by both `matmul(x, w)` and a pointwise `relu(w)`. The pointwise plan is appended, the matmul consumer trips the new gate, and *both* are dropped. The pointwise relayout was accepted at 67df28b and is unaffected by the weight rule. Mirror hole: because the gate only sits under `is_matmul`, a restickified graph input consumed *only* by pointwise ops is still relayed out, so the docstring's promise at `:201` holds for matmul consumers alone. Silent drop (slower), not wrong numbers.

**2. `demote()` turns an incomplete LX teardown from a crash into a silent skip.** `scheduler.py:507-512`. It now reads the **raw** `buffer.layout` and `continue`s when the layout is None or lacks `allocation`. `discard_lx_relayout_group` has already run at `:505`, so a skipped member leaves exactly the state this pass exists to prevent: registry entry gone, but the buffer still carrying `allocation['lx']` and a non-`None` `lx_view` â which is precisely what `spyre_kernel.py:770-773` keys off to emit per-core ownership. `hasattr(layout, "allocation")` is a proxy for `isinstance(layout, FixedTiledLayout)`, so it silently skips wrapper layouts such as `MutationLayoutSHOULDREMOVE` whose inner `real_layout` *does* hold LX state â and this repo demonstrably has such wrappers over `FixedTiledLayout` (`insert_restickify.py:431` and `enforce_indirect_access_layout.py:54` both call `.real_layout()`). At 67df28b the same case raised `AttributeError`. Whether it is reachable on a relayout group member is unproven, but the direction is crash â silent, and the fix is two lines. **Trap for whoever fixes it:** `real_layout` is a *method*, so `getattr(layout, "real_layout", layout)` returns a bound method, `hasattr(..., "allocation")` is still False, and the buffer is still skipped â the code looks fixed and isn't. Use `buffer.get_layout()`, which is what every spyre codegen path already uses (`spyre_kernel.py:988`, `:1018`, `:1145`).

**3. The backfilled `TensorWorkDivision` mixes key types, violating the invariant this same commit documents.** `compute_ops.py:589-591` pairs `sdsc_spec.work_slices` (Symbol-keyed, `superdsc.py:1059`) with `sdsc_spec.core_id_to_work_slice` (str-keyed â `core_to_slice_mapping` does `result[str(dims[dim])] = coordinate`, which is why `superdsc.py:978` needs `core_map[str(dim)]`). The docstring added at `op_spec.py:144-149` in this very commit says "Both mappings have the same symbol keys." Unreachable today for two independent reasons â `_tensor_core_map` returns `{}` unless `opfunc == "shuffle"` (`compute_ops.py:1107`), and shuffle args always come through `_finalize_tensor_work_divisions` â and when it does fire it raises `KeyError`, not wrong numbers. Latent trap, not a live bug. The field annotation `core_id_to_work_slice: dict[Symbol, Any]` (`superdsc.py:117`) is simply wrong and hides it.

**4. The numerics test lost coverage while gaining it.** `tests/inductor/test_work_division_hint.py:653` applies `rtol=2e-2, atol=1e-1` to **both** outputs, though only the new `bmm` needs slack â the `relu` output is bit-exact and is now checked at 10% absolute tolerance. And the workload was replaced wholesale (2-D 128Ã256 pointwise+pointwise â 3-D 8Ã32Ã64 pointwise+bmm), so the two-pointwise-consumer fan-out â the case `insert_clone_before_consumer` was written for â is no longer covered numerically anywhere in the suite. Everything else in that test diff is strictly stronger.

Two changes look like regressions and are not. The swap of `_views_fit_coordinates` for three `work_division_from_view` calls (`lx_relayout.py:300-319`) rejects strictly more edges than 67df28b, including a new producer-side check â but that trades a mid-codegen `ValueError` (the same function runs at `spyre_kernel.py:771`) for a quiet plan drop, which is the safe direction. And the new `raise` at `superdsc.py:993-996` cannot fire on the operation-level branch at all: `work_slices` and `dim_splits` are built from the same key set and mutated in lockstep at every injection site, so their products are equal by construction.

## What remains, in order

**1. Unwrap the layout in `demote()` instead of skipping it.**
`torch_spyre/_inductor/scheduler.py:507-512`
Replace the raw `getattr(buffer, "layout", None)` + `hasattr` guard with `buffer = V.graph.try_get_buffer(name); if buffer is None: continue; layout = buffer.get_layout()`, then clear `allocation['lx']` / `lx_view` / `lx_consumer_is_matmul` unconditionally. Log a warning on any residual give-up, so a demotion that accomplishes nothing announces itself. Apply the same fix to the untouched twin at `allocator.py:944-952`, which still does `getattr(graph.get_buffer(name), "layout")` with no guard at all â one teardown, one failure mode. Best as a shared `clear_lx_state(graph, names)` helper in `lx_relayout.py`.
**Verify:** a group member whose codegen-visible layout is a `FixedTiledLayout` behind a wrapper comes out of `demote()` with `lx_view is None` and no `"lx"` key. Add a scheduler test with a wrapper layout â the existing fake graph at `test_work_division_hint.py:757+` only supplies `SimpleNamespace` layouts that always have `allocation`, so neither new branch is covered.

**2. Hoist `_is_activation_source` out of the consumer loop.**
`torch_spyre/_inductor/lx_relayout.py:288-296`
Evaluate it once, right after `source_view` / `num_cores` are computed (~`:254-258`). If weights must never be relayed out, `continue` the outer source loop; if only the matmul edge should be rejected, keep the flag and reject that consumer with `continue`, not `break`. Either way the outcome stops depending on which consumer the graph happens to visit first.
**Verify:** a source with one matmul consumer and one pointwise consumer emits the pointwise plan (or, deliberately, neither) â and the answer does not change when the two consumers are reordered in the graph. Add the reject-side test that is still missing in both this branch and the reference: a `restickify(<graph input>)` producer feeding a matmul must emit no plan.

**3. Assert on a dropped split instead of defaulting it to 1.**
`torch_spyre/_inductor/codegen/superdsc.py:823-826` and `:985-990`
Both re-key an LX override with `.get(dim, 1)`, so a dim the re-key fails to carry is silently demoted to unsplit â and the failure then surfaces one step later as `ValueError: tensor ownership uses {...}, expected 32 cores` (`:993`), which points the reader at the ownership map rather than at the re-key that lost the dim. Raise at the drop, naming the dim and both key sets.
**Verify:** feed an override carrying a dim absent from `mapping_dims` and confirm the error names that dim, not the core count.

**4. Write down the B1 invariant, or settle the bundle question.**
`torch_spyre/_inductor/scratchpad/allocator.py:889-894`
One sentence at `_append_lx_relayout_destinations` naming what the half-tick model leans on: *the even tick is the slot `insert_clone_before_consumer` occupies in `graph.operations`, and `demote_incoherent_lx_buffers` guarantees the copy stays its own node.* The open question underneath is not this feature's: `spyre_fuse_nodes` (`fusion.py:41-72`) packs consecutive Spyre nodes into one SuperDSC bundle and runs *after* the demotion pass (`passes.py:289`), so producer DSC and copy DSC do share a bundle. If DSCs inside a bundle are not serialized, then every adjacent-lifetime reuse in the allocator is equally unsound â a defect in the base lifetime model, to be fixed for all buffers, not patched into the relayout path.
**Verify:** the comment exists, or a separate issue names the bundle-ordering guarantee.

**5. Fix or delete the backfill.**
`torch_spyre/_inductor/codegen/compute_ops.py:589-594`

## Merge readiness

Mergeable after two items. The one thing on this branch that produced wrong numbers â B6's inverted sub-dimension radix â is fixed in the correct direction and pinned by a test that fails under the old code, and B1, the first pass's highest-severity item, does not survive scrutiny: the relayout copy occupies a real operation slot in the same index space the liveness model walks, so it adds no assumption the allocator was not already making. B3, B4 and B5 are genuinely closed; B7 is closed in behavior but only by accident of class layout, and B2 is a faithful port whose remaining hole it shares with the reference. What I would not merge without fixing is item 1, the `demote()` silent skip â it is the only change here that converts a loud failure into a quiet one on the path whose entire job is to pull incoherent buffers back out of LX, and its fix has a trap (`real_layout` is a method) that will otherwise be "fixed" without being fixed. Item 2, the `break`, is cheap and should go with it: today a single weight-fed matmul silently discards every unrelated relayout for the same source, and which plans survive depends on graph visit order. Items 3 through 7 are follow-ups; none of them can produce a wrong number on an ordinary graph.
