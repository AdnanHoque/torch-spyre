AIU Ring Speed

The 36 GB/s we see on the production relayout is not a ring limit — it is an all-to-all contention floor. Give the same ring a uniform, neighbor-to-neighbor movement pattern and it delivers its full raw bandwidth.

01The hardware, in one paragraph

The AIU packs 32 cores on an L3 / RIU BiRing — a bidirectional ring, bandwidth quoted per direction. Any data that must change which core owns it — a relayout, a shuffle, a collective — moves core-to-core across this ring via one op, STCDPOpLx. The cost model treats the ring simply: raw bandwidth is 128 GB/s/dir in perfmodel.cpp (sysdef.cpp:216), up to 166 in the dd2 RIU-To-RIU-Link JSON that matches spec. Per-hop latency is modeled as λ = 0. So there is exactly one mechanism that can move the effective rate off raw: per-link contention. When several transfers must cross the same ring segment, they serialize. Everything below is that one mechanism, measured.

02The mechanism: two patterns, same ring

The centerpiece. Both panels are the same 32-core ring. What differs is only the shape of the movement — and that shape is the entire story.

Figure 2 — the centerpiece. Same ring, same op (STCDPOpLx), same total bytes. Left: a permutation of core-ownership. 524 movement descriptors, each source feeding 7–9 destinations and each destination gathering from 4 sources; every physical ring link ends up carrying 4–9 transfers that must take turns. Right: a uniform rotation — each core sends one contiguous block to c+1. Exactly one transfer per link, nothing waits. The spaghetti versus the clean rotation is the 36-vs-130 gap.

Physically the red transfers do not fly across the interior — they route along the ring. Drawing them as chords just makes visible what the scheduler cannot avoid: a permutation forces many logical transfers onto the same shared arcs. That sharing is contention, and contention is the only knob the model has.

Figure 3 — why sharing divides bandwidth. With λ=0 latency, the ring is a pure pipe: put N serialized transfers on one segment and each gets raw/N. All-to-all crowds 4–9 onto the busy links, which is exactly the arithmetic that lands the measured floor near 36 GB/s.

03How every number here was obtained

Not from a spec sheet or a debug counter — from moving real bytes on the device and measuring the slope. The trick isolates the transfer from all fixed program and host overhead.

Figure 5 — the additive-differential slope. Fixed cost is the intercept; only the move scales with K, so Δtime/ΔK is the pure per-move time.

The recipe

1 — fire a real relayout; capture its device-tensor arguments.

2 — splice K extra copies of the relayout's execute line into the compiled bundle.mlir; recompile.

3 — per-iteration-synced wall + device time; fit the line. slope = Δtime / ΔK isolates the move.

4 — ρ = bytes_moved / slope.

The honor control

Sweep the moved bytes. The slope must change with bytes — that proves the runtime is really moving them, not absorbing a cosmetic edit. Every ρ below passed this control.

04Three findings

1 · The scatter is slow

The production relayout runs at ~36 GB/s — ~22% of raw. Decomposed: ~70 µs fixed per-move overhead + ~55 GB/s contended streaming. The explicit stcdp_range carrier and the auto-synthesized dl-dsc path (backend builds the same STCDPOpLx from a coordinate mismatch) both hit this identical floor. dl-dsc's end-to-end win on a fused SwiGLU is ~1.4× at the moved edge / ~1.7% of the layer: one 13.1 MB activation kept on-chip instead of an HBM round-trip.

2 · Burst size is not the lever

Enlarging the per-descriptor burst 8 → ~800 sticks on the same scatter gave 1.0× — zero gain, honor-controlled. The deeptools BurstEfficiency.def table is a scheduler selection heuristic for picking chunk parameters, not a bandwidth multiplier: perfmodel runs the ring at raw 128 for every pattern. So 36 is not a burst derate — it is contention, full stop.

3 · The uniform shift is fast

A uniform single-hop rotation escapes the floor and reaches the raw band: 54 → 90 → 130 GB/s as volume rises (4 → 8 → 16 MB), with a ~250 GB/s streaming asymptote (31 uncontended ring segments in parallel). At bytes matched to the scatter (~8 MB): 90.5 vs 36 = 2.5×. At 16 MB, 130 sits dead center of the model's 100–145 raw-ring prediction. The contention model was right.

The measured points (54, 90, 130) ride the curve eff = B / (58µs + B/250): the fixed ~58 µs overhead amortizes and the rate climbs toward the ~250 GB/s streaming asymptote. 06The verdict

~36 GB/s is an all-to-all contention floor, not a ring limit. The BiRing delivers its full raw bandwidth (~130–250 GB/s) for uniform and ring-pipelined patterns, and chokes to ~36 only when a permutation crowds 4–9 transfers onto shared links. The contention model was right; burst size never mattered.

Implications

  • Weight-carousel rotation transport is confirmed fast. It is a uniform p→p+1 shift, so the ring is not a bottleneck for it.
  • Ring-pipelined all-gather / LSE-fold is viable. A bucket-brigade of contiguous uniform hops runs in the raw band, not the floor.
  • The production scatter relayout is genuinely stuck at ~36. The lever there is ring-distance-aware placement — assign core-ownership so fewer transfers cross-cut the same links — not burst tuning.
  • The cost model's ring term should be pattern-aware. One ρ is wrong: use a contention-scaled term, ~36 for all-to-all and ~130+ for uniform / pipelined, rather than a single constant.
