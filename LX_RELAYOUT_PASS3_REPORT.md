# LX relayout — third review pass

Reviews `cc90711b` ("Harden LX relayout fallback handling") against `c60f5d81`. This commit
implements the nine-item fix list agreed after the second pass — six items proposed by the
author, three added from `LX_RELAYOUT_PASS2_REPORT.md`.

All nine landed. Nothing here produces wrong numbers, so this does not block on correctness.
The finding worth carrying forward is a pattern rather than a defect: **three of the nine
close the symptom while the mechanism survives**, and in two cases the result is a guarantee
that reads as enforced and is not.

- **#8, the co-optimizer gate, is a tautology.** `supports_lx_relayout` is read only inside
  `ScratchpadAllocator._prepare_buffers`, which neither co-optimizing allocator reaches —
  `StrategyBCoOptimizingAllocator` overrides `plan_allocation` and calls `_generate_buffers`
  directly; `CoOptimizingAllocator` overrides `_prepare_buffers` without `super()`. The new
  assert is vacuous for the same reason. Behaviour is still correct, because
  `collect_lx_relayout_plans` has exactly one caller — but the guarantee is as unenforced as
  before the fix.
- **#1's premise was wrong, and it was mine.** I asserted `get_layout()` was the correct
  accessor because it avoids the `real_layout` bound-method trap. It does avoid that trap, but
  it does not unwrap either: this tree calls `get_layout()` and *then* isinstance-tests
  `MutationLayoutSHOULDREMOVE` before `.real_layout()` (`pass_utils.py:60-84`), and asserts the
  wrapper comes straight off `get_layout()` (`pass_utils.py:1298`). It remains the right call
  here for a different reason — mutation layouts cannot reach that path — so keep the change
  and state the invariant rather than reinstating the deleted guards.
- **#3 is fixed on a branch unreachable in production**, and the real str/Symbol boundary at
  `core_mapping.py:63` is untouched.

Two fixes came out better than specified: **#2** also closed a bypass that existed at
`c60f5d81`, where a restickified graph input feeding only pointwise consumers was
relayout-eligible.

## Introduced by this commit

**No new defect.** Not a silent-wrong-numbers, not a silent drop, not a crash on any reachable path. Every semantic change was enumerated and checked: the activation hoist only *removes* plans; the `compute_ops` lookup feeds an unreachable backfill; the `superdsc` assert is error-only and inert on non-relayout graphs (`spyre_kernel.py:953-956` nulls `work_division` for every op that is not a relayout identity); the `get_layout()`/`.layout` swap is a no-op for `FixedTiledLayout`; `clear_lx_relayout_state`'s body is byte-identical to the two inlined versions it replaced; the `supports_lx_relayout` gate is inert; the registry-discard swap is equivalent.

Two narrowings are worth recording, neither a defect today:

- **`compute_ops.py:589-597` can now `KeyError` where the old code could not.** The old form was two dict references (`TensorWorkDivision(sdsc_spec.work_slices, sdsc_spec.core_id_to_work_slice)`) â incapable of raising. The new comprehension indexes `core_id_to_work_slice` once per `work_slices` key, and it is evaluated **eagerly on every `generate_sdsc` call, production included** (only its *consumption* at :599-600 is dead). I verified the inclusion is total: `sdsc_iteration_space`, `dim_splits`, and `work_slices` are seeded from the same `symbol_mapping` (`superdsc.py:1040, 1057, 1062`) and every later insertion touches all three in lockstep (mb injection :1081-1084, P=1 gather :1106-1109, stick dim :1133-1141, restickify padding :1209-1211), and `core_to_slice_mapping` emits `str(dim)` for all of `mapping_dims` (`core_mapping.py:66`). All nine in-tree hand-built `SDSCSpec`s also satisfy it. So nothing breaks â but a future change that adds a dim to one dict without the other turns this into a hard `KeyError` rather than a silent mismatch. Worth a comment, not a fix.
- **The pointwise-relayout bypass closed by fix #2** (see the table) is a behavior change that no test covers in either direction: `git grep _is_activation_source -- tests` is empty, and none of the four relayout tests (`test_work_division_hint.py:563, 629, 689, 769`) builds a restickify source.

## Still open

**Moderate â the atomicity precondition is undocumented and untested.** `_generate_buffers` does, for every plan, `ncores[name] = plan.num_cores`, `ncores_reasons.pop(name, None)`, and `mem_usage[name]["core_div_mismatch"] = False` for **both** source and destination (`allocator.py:826-835`). That is the relayout feature switching off the pre-existing guard that would otherwise keep a disagreed-upon buffer in HBM. It is sound only because `collect_lx_relayout_plans` is all-or-nothing per source, carried entirely by the `for consumer ... else: result.extend(source_plans)` at `lx_relayout.py:276, 339-340` â one loop construct with seven `break` sites and one `continue` (:299-300) that must *not* abandon the source. Nothing tests it; `collect_lx_relayout_plans` is imported by zero tests (the test file imports only `LXRelayoutPlan` and `work_division_from_view`, :46-49). To be precise about the stakes: a partial plan would *not* immediately give wrong numbers â `demote_incoherent_lx_buffers` would catch the un-relayouted consumer, since it is absent from `copy_reads` and its view differs from `expected` (`scheduler.py:498, 524-544`) â so the realized failure is a silent drop plus a wasted shuffle. But demote is the *only* backstop, and it is backstopping a guard the planner deliberately disabled. Fix: one stub-graph unit test (one source, two consumers, second ineligible, assert **zero** plans), plus a comment at `allocator.py:826` naming the precondition.

**Cleanup â `supports_lx_relayout` is inert (item #8).** Real enforcement already exists via `materialize_lx_relayouts` with an empty plan list (`allocator.py:1033`, `lx_relayout.py:350-352`), so there is no runtime hole. What remains is a class attribute that does no work on the only two classes that set it, and an assert that cannot fail. Either route both co-opt allocators through the base `_prepare_buffers` so the flag becomes load-bearing, or delete both and leave a comment saying the bypass is structural. Note that the tempting alternative â `assert not materialized_lx_relayouts(graph)` at the end of `plan_allocation` â would be *equally* tautological, because `_push_allocation` already cleared the registry by then; it only means something placed **before** the push.

**Cleanup â the key-type split at its source (item #3).** Normalize at the producer: have `core_to_slice_mapping` return `dict[Symbol, Expr]` (`result[dims[dim]] = coordinate`, `core_mapping.py:63`), drop the `str(dim)` round-trip at `superdsc.py:981`, revert the annotation at `superdsc.py:117`, and delete the dual-key lookup. The in-tree fixtures are already Symbol-keyed, so they get simpler. **Do not** take the alternative of deleting `compute_ops.py:589-600` outright â that breaks the build: `_build_coord_info` (`compute_ops.py:1083-1088`) asserts `tensor.work_division is not None` unconditionally, and `test_coarse_tiling.py:548` builds an `SDSCSpec` whose args have none. While there, add a duplicate-stringification check to `core_to_slice_mapping`, which today validates only `len(dims) != len(splits)` (`core_mapping.py:39-41`); two Symbols stringifying identically would silently collapse into one ownership entry. Theoretical â sympy caches by name plus assumptions and nothing here varies assumptions â but it is the exact silent-wrong-ownership shape this area is dangerous for.

**Cleanup â teardown and accessor consistency.** Give `clear_lx_relayout_state` an honest name and contract. Two traps to note: (a) its docstring scopes it to "an LX relayout buffer", but `scheduler.py:546` routes *every* `_lx_resident` write dep through it â the commit's own test demotes `ordinary_source`, which has no plan (test:835) â so it is the general LX-demotion primitive; adding a `keep_allocation=True` mode to serve `materialize_lx_relayouts` would, if mis-wired, silently stop demoting ordinary incoherent buffers, which is the pass's actual correctness job. Use a separate function, not a flag. (b) The `get_layout()` sweep is partial â four sibling sites still use the raw attribute, including the *write* path that stamps the state the whole feature depends on (`lx_relayout.py:232-234, 367-371`), plus `scheduler.py:325` and `allocator.py:228`. Converting one and leaving four reads as "the others were checked and deliberately left". `allocator.py:228` is the interesting one: its `None` default swallows `MutableBox.__getattr__`'s raise, so on a TensorBox a stale `allocation["lx"]` would survive the pop instead of failing loudly â not reachable today, but the exact failure mode the accessor swap was meant to remove.

**Nit â untested branches.** Both new `buffer is None` guards (`scheduler.py:331-332, 513-514`). The "invalid relayout copy" branch (`scheduler.py:487-495`): none of its six disjuncts can evaluate true in any existing test case, since the destination node is always one read named `source`, one write, and differing stub views (test:784). Note the fused-identity scenario that motivates that branch **cannot occur** in this pipeline â `SpyreHeuristics.can_fuse/_vertical/_horizontal` all `return False` unconditionally (`choices.py:36, 45, 54`), as do `SuperDSCScheduling` (`scheduler.py:574, 583`) and `CountedLoopSchedulerNode.can_fuse` (:92); demote flattens to inner `SchedulerNode`s anyway (`scheduler.py:455-460`), making the read/write counts fusion-invariant; and the one custom fuser `spyre_fuse_nodes` (`fusion.py:41`) runs *after* demote in the same list (`passes.py:289`). It is a defensive guard for a shape nothing can generate â do not send the next reader hunting it.

**Nit â `_is_activation_source` is still one-hop** (`lx_relayout.py:208-215`). `restickify(w) -> to(dtype) -> matmul` passes trivially because the planned op's short name is not `restickify`. It is a policy filter, not a correctness gate â every guarantee here is orthogonal (`_compatible_partitions` :148-187, the three `work_division_from_view` ValueErrors :84-98 caught at :327, `superdsc.py:996-999`, and demote). The leak costs a wasted shuffle of a weight. Rename it to say what it is (`_worth_relayouting`) and put the cost rationale in the docstring.

**Deferred â clone rollback. Recommendation: leave it, and close the #3615 question in writing.** Both halves are settled with evidence. (a) **#3615 is entirely moot.** b4ae70f touches only `torch_spyre/_inductor/patches.py`, popping `aten.copy.default`/`clone.default`/`clone.out`/`alias.default` out of Inductor's `noop_registry` (`patches.py:147-152`), which is consumed by the FX-level `remove_noop_ops` in `torch._inductor.fx_passes.post_grad` â before lowering. The relayout clone is created at IR level by `insert_clone_before_consumer` (`lx_relayout.py:363`, via `graph_editor.py:229`) inside `_push_allocation`, long after FX. The two never meet. (b) **The surviving clone is perf-only, not a correctness leak.** After `clear_lx_relayout_state`, `is_lx_relayout_identity` returns False (it requires `"lx"` in both allocations, `op_spec.py:203-215`), and `spyre_kernel.py:771-775` passes `None` to `work_division_from_view` because `"lx" not in tensor.layout.allocation` â so both args fall back to the operation-default division and the op emits a plain `identity`, not a `shuffle`. `hbm_pool_planning` runs immediately after demote (`passes.py:289`) and gives the orphan an HBM home, exactly as the docstring at `scheduler.py:434-436` claims. Cost: one redundant full-tensor copy and one intermediate buffer, only on a graph that already lost LX residency. Reclaiming it requires sweeping *before* scheduler-node construction, rewriting consumers' deps back to the source â which the comment at `scheduler.py:509-510` already says. Add a TODO pointing at that constraint so the next reader does not re-trace it.

## Merge verdict

**Ship it.** Three passes in, the honest answer is that this commit does what it was asked to do and introduces nothing wrong. Six of nine fixes are clean; the three that are not (#3, #6, #8) all share the same harmless shape â the symptom is closed and the mechanism lives elsewhere, but in each case the *outcome* was already correct by construction, so the residue is inert code rather than a hole. The two items that changed real behavior (#2's hoist, #4/#9's tolerance and parametrization) both move in the safe direction: strictly fewer relayouts, and strictly tighter numeric checking on the one copy whose ownership map was previously observed only through a `bmm` at `rtol=2e-2`. I could construct no path â reachable or otherwise â from this diff to wrong numbers. The one item worth a follow-up ticket rather than a merge block is the atomicity precondition at `allocator.py:826-835`: the planner disables the core-division mismatch guard for every planned buffer, that is sound only because `collect_lx_relayout_plans` is all-or-nothing per source, and that property is carried by a single `for/else` with zero test coverage. It is not a blocker â `demote_incoherent_lx_buffers` backstops it, and no current graph can violate it â but it is the one sentence in this feature that, if it ever stops being true, fails in the expensive direction. Land the commit; open a follow-up for the stub-graph atomicity test plus the comment naming the precondition, and fold the #3/#8 cleanups into it.
