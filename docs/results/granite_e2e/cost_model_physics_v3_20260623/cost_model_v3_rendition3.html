Substrate · first principles

01 The machine and the split

The AIU is 32 cores, and each core is one 8×8 weight-stationary systolic array — an MPE. The whole cost model exists to answer one question: given a matmul, how do you carve its iteration space across those 32 arrays so that every array stays fed?

Reading the model takes four facts about the silicon, and this section covers all four: how the array computes (weights held still, tokens streaming through), what a stick is (the 128-byte contiguous unit that measures N and K but never M), how the four split axes map onto hardware (B·M·N·K), and what N-split and K-split cost in traffic (the broadcast cohort and the PSUM ring). Every term the later sections score is a weighing of these four.

One color law runs through every figure from here on. In [B,M,K] @ [B,K,N] → [B,M,N] the weight tile [K,N] is loaded into the array and stays put — stationary, resident, drawn warm. The M rows (tokens) stream through it — in flight, drawn cool. Warm is memory that holds; cool is data that moves.

1 · The array holds the weights still

A systolic array does not fetch weights per multiply. The weight sub-tile is latched into the cells and left there; token rows then flow past the stationary weights, one wavefront at a time. The array ingests M in passes of _PT_ROWS = 8 rows. Each core is handed m_t = M / M_split rows, so it runs pt_passes = max(1, m_t / 8) passes over its resident weight.

Every array has a fixed fill-and-drain latency — the wavefront must propagate in before results propagate out. That fixed cost is amortized across passes, so few rows per core means the overhead dominates. The model captures this as a derate: pt_eff = min(1, (pt_passes / 5)^0.25). Full efficiency wants _TARGET_PT_PASSES = 5 — 40 rows per core. The hard gate the whole model turns on sits lower, at 16 rows (two passes, _M_TILE_UNDERFILL_TARGET = 16): below it you pay pure startup/drain tax. Over-split M and you starve the array — exactly the decode failure mode the later sections dissect.

2 · The stick — the unit of N and K, never of M

Spyre memory is 128-byte aligned. One stick = 128 bytes = 64 fp16 elements, the hardware's atomic contiguous chunk. The two stationary-facing dimensions are laid out and counted in sticks: N (weight and output columns) and K (the contraction / activation depth). The cost model reasons about N-tiles and K-tiles in stick and element terms because that is how they sit in memory.

M is categorically different. M is the streaming dimension — a row of M is fed through the array over time, not stored as a contiguous run. M is never a stick; it is counted in passes through the array. Reading this backwards — treating M as the contiguous, coalesced axis — is a classic and expensive mistake: it makes M-splitting look free when it is in fact the axis that starves the array.

3 · The split: dividing the iteration space over 32 cores

Planning a matmul means dividing its logical iteration space [B,M,K] @ [B,K,N] → [B,M,N] across at most 32 cores as B_split × M_split × N_split × K_split, product ≤ 32. The chip artifacts write this as 1_4_8_1 — meaning 1·4·8·1, i.e. B1, M4, N8, K1, spending all 32 cores as a 4×8 grid. Each axis exposes a different parallelism and charges a different physical cost:

Axis Splits the… Exposes (parallelism) Costs (what it stresses)
M token rows PT rows → array fill (m_t = M / m) too few rows/core → PT startup/drain, pt_eff falls
N output columns output-column parallelism broadcast fanout → HBM cohort contention past 8
K contraction reduction parallelism (k−1) partial-sum hops around the PSUM ring
B batches whole-batch parallelism for true BMMs batch-split overhead; only helps when per-item M is tiny

4 · Two traffic costs: the cohort and the ring

M-split moves almost no data — its cost is the array-fill derate above, not traffic. The other two splits move data. N-split creates broadcast cohorts: every core owning a slice of the same output tile needs the same input operand, so one operand fans out to a group of cores. Up to _COHORT_LIMIT = 8 cores that broadcast rides the shared link for free; past 8 the link contends and effective bandwidth falls, which the model prices as (fanout / 8)^0.75.

K-split creates the PSUM ring: splitting the contraction means k cores each compute a partial sum of the same output tile, and those partials must be reduced — (k−1) hops of accumulator traffic around the ring. The v3 model charges this per-core output tile, not the whole output tensor, so a small, tile-improving K-split (like decode QKT's k=2) is no longer over-punished.

Substrate constants

cores = 32 · _PT_ROWS = 8 · _TARGET_PT_PASSES = 5 (40 rows fills the pipe) · _M_TILE_UNDERFILL_TARGET = 16 · stick = 128 B = 64 fp16 · _COHORT_LIMIT = 8 · peak ≈ 1.536 MMAC/µs/core (98.304 TFLOP/s ÷ 2 ÷ 32) · HBM = 204.8 GB/s

Those are the four facts. The whole cost model is a weighing of them — and the one that decides nearly every hard case is the first: rows per core versus the array's appetite. The next section turns that number into a gauge you can read at a glance.

COST MODEL · SCORING

02The score: three physical costs

Every legal split gets exactly one number, and the planner keeps the split with the smallest number. In physics v3 that number is a plain sum of nine microsecond terms — three that estimate real hardware time, six that shape the per-core tile — and lower wins.

This section takes the three physical terms: what wall-clock each models, and why each is a correction on the model v3 replaced (commit 196d768), which instead multiplied a four-term estimate by a batch dial. First, the shape of the score itself.

nine terms, summed. lower wins.
add, don't multiply In 196d768, any candidate carrying a batch factor b=8 had its whole estimate multiplied by 8^1.4 = 18.4× — batch parallelism was priced out before it could compete. v3 charges that same split the additive log2(8)·10 = 30 µs, so it competes term-for-term and wins exactly where it earns a healthier tile, like decode attn@V's 8·4·1·1. The physical three below are where that currency is earned.

01 · compute_us — MACs over a derated peak

The honest floor: count the per-core MACs and divide by per-core peak. Peak is (98.304e12 ÷ 2 ÷ 32) ÷ 1e6 = 1.536e6 MAC/µs/core (DL16 throughput, FLOP→MAC, split over 32 cores). But the 8×8 PT array streams M in passes of _PT_ROWS=8 rows over a stationary weight tile; if the per-core tile m_t = M/M_split is too short, pipeline startup and drain are amortized over too little work. So peak is scaled by an efficiency factor that rises sub-linearly toward one:

m_t       = M // M_split
pt_passes = max(1, m_t / 8)
pt_eff    = min(1, (pt_passes / 5) ** 0.25)      # v3
compute_us = (B*M*N*K / cores) / (1.536e6 * pt_eff)

Against 196d768, two things changed. The old derate used a sqrt (0.5) exponent and targeted 8 full passes; v3 uses a gentler 0.25 exponent and targets 5. The old curve punishes short M far harder and saturates far later. v3 deliberately makes the compute derate a soft nudge and moves the sharp "too few rows" signal into a dedicated one-sided penalty (m_tile_underfill, next section) rather than overloading one term with two jobs.

physics v3 · (x/5)^0.25 196d768 · (x/8)^0.5
worked · prefill MLP-down 1·8·4·1 Shape 1×512×4096×12800: 2.68e10 MACs ÷ 32 cores = 8.39e8 MACs/core. m_t = 512/8 = 64 → 8 passes → pt_eff = 1.0 (saturated), so compute_us = 8.39e8 / 1.536e6 = 546 µs. Here 8 passes ≫ 5, so both models sit at pt_eff = 1 and agree at 546 µs; the curves only diverge once M is short — the decode regime, where v3's gentler 0.25 keeps more of the peak.

02 · hbm_us — bytes over bandwidth, weight once

Bytes moved over the LPDDR5 link at 204.8 GB/s: activation B·M·K, weight K·N, output B·M·N, all fp16. Two corrections over 196d768:

weight_batches = 1 if shared_weight else B        # (1) counted once
bytes  = (B*M*K + weight_batches*K*N + B*M*N) * 2
fanout = max(m, n) if shared_weight else n        # (2) bmm keys on n
cohort = max(1, (fanout / 8) ** 0.75)
hbm_us = bytes / (204.8 * 1000) * cohort

(1) Shared weight loaded once. A projection or MLP RHS is the same matrix for every token, so it is counted 1×, not B×. The old model counted B·K·N unconditionally, over-charging any folded shared-RHS bmm with B>1. (2) Broadcast contention. Splitting an output dim broadcasts an operand to a cohort of cores; past _COHORT_LIMIT=8 they contend for the link. v3 makes that falloff sub-linear (^0.75) and, for true BMMs, keys it to n alone — so head/batch parallelism, which never widens the shared broadcast, pays nothing. The old model used a linear max(m,n)/8 for every matmul.

physics v3 · (f/8)^0.75 196d768 · f/8 linear
true-bmm cohort Because fanout keys on n for a true BMM, a 8·4·1·1 batch+M split (attention) sits at fanout = n = 1 → cohort ×1.0: head parallelism is free on this term. The same split under the old linear rule (max(m,n)=4) still reads ×1.0 here, but a pure-M 1·32·1·1 jumps to ×4.0.
worked · prefill MLP-down 1·8·4·1 Bytes = (512·12800 + 12800·4096 + 512·4096) · 2 = 122.2 MB; fanout = max(8,4) = 8 → cohort ×1.0; so hbm_us = 122.2e6 / 204800 = 597 µs. The 12800·4096 weight is counted once — the dominant operand, charged for a single load across all 512 tokens.

03 · psum_us — reduction hops, per core tile

A K-split hands the reduction to k cores, each producing a partial sum for the same output tile. Those partials are combined around a ring in k−1 hops. The correction is what each hop is charged against:

output_elems_per_core = (B*M*N) / max(1, b*m*n)   # per-core tile, not whole output
coeff  = 1e-3 if shared_weight else 1e-4
psum_us = max(0, k-1) * output_elems_per_core * coeff

v3 charges each hop the per-core output tile — the whole output divided by the b·m·n cores that split it. 196d768 charged (k−1)·(B·M·N)·1.4e-4 over the whole tensor, so every K-split looked enormous and the planner never took one. That single miscount is why the decode QK^T reduction split was unreachable in the old model.

worked · decode QK^T 8·2·1·2 Shape 64×32×576×128, true-bmm, k=2: elems/core = 64·32·576 / (8·2·1) = 73,728, so psum_us = 1 · 73,728 · 1e-4 = 7.37 µs. The old whole-output charge on the identical split is 1 · 1,179,648 · 1.4e-4 = 165 µs. Making a genuinely useful reduction split affordable is what unlocks the 126% decode-QK^T fix — the per-core correction, not a new heuristic.

Three terms, three limits: MAC throughput, HBM bytes, PSUM hops. Each is a first-principles cost, each fixed a specific over-charge in 196d768, and all three now compete on one additive scale. The six shaping penalties — and the M-fill gate that arms half of them — are next.

SOFT TERMS · TIE-BREAKS & GUARD RAILS

03 The guard rails

The physical trio — compute_us, hbm_us, psum_us — estimates where the microseconds go. But two splits can score near-identical physics and still compile to very different device kernels. Five additive tie-breaks decide between them — in score order, terms 04 · 05 · 06 · 08 · 09 — plus one gated shape family, term 07, that only arms once the array is already full (it travels with the M-fill gate, §7).

Every guard rail shares one signature: max(0, log₂(target ÷ actual)) · penalty — it charges only for falling short of a target and clamps to zero the instant the tile meets it. That one-sidedness is the whole design: a toll that can never go negative, and never fires above target, punishes a starved tile without ever taxing a healthy one. The old model steered by global levers instead — a batch_penalty that multiplied the entire estimate and a hard core-count guard that could veto the cost argmin outright. v3 retires both for additive, one-sided tolls.

TERM 04 m_lane_underuse_us max(0, log₂(target_m ÷ m)) · 10

The lowest-weight nudge: expose enough M lanes to keep the stationary weight fed. target_m = max(4, min(max_cores⁄2, M⁄32)). Fires only while m < target_m; zero once the lanes are there.

TIE-BREAK
TERM 05 m_tile_underfill_us max(0, log₂(16 ÷ m_t)) · 30

The decode workhorse. m_t = M ⁄ M_split; below 16 rows/core the PT array pays startup/drain each pass. Decode attn@V's old 1·32·1·1 → m_t = 2 → log₂(16⁄2)·30 = 90 µs. Exactly 0 at m_t ≥ 16.

ONE-SIDED
TERM 06 wide_n_us max(0, log₂(n_t ÷ 512)) · 25

n_t = N ⁄ N_split. Only the over-wide output side is charged — past 512 elems/core the generated kernel loses schedule efficiency. Short-M and moderate-N picks pay nothing, so it never pulls a choice off a PT-friendly M tile.

OUTPUT-SIDE
TERM 07 large_m_tile_shape_us filled_m_tile_factor · max(0, log₂(K∕N)) · log₂(n) · 20

A family of three shape guards (true-BMM value-split shown) that arm only once m_t ≥ 16 fills the array. This is the prefill-vs-decode "opposite instincts" story — covered with the M-fill gate.

The soft ramp that replaced a hard cliff

core_underuse_us = max(0, log₂(32 ÷ cores_used)) · 150 is the most consequential guard rail because of what it replaced. The old planner ended on a hard trade-down guard — if math.prod(new_splits.values()) < math.prod(splits.values()): return splits (wd_oldbaseline.py L1110-1112). Any split the cost model preferred that used fewer than 32 cores was vetoed and swapped for the default distributor's pure-M 1·32·1·1 / 32·1·1·1. Using every core looked responsible; it starved the array whenever the healthiest tile wanted fewer, larger lanes.

v3 turns the binary veto into a graded toll: a 16-core split costs 150 µs, an 8-core split 300 µs — real, but payable. If a lower-core tile saves more in compute and underfill than the ramp charges, it wins. The cliff never let it try; the ramp lets the physics decide.

Additive batch, not a multiplier

batch_split_us = log₂(max(1, b)) · 10 is charged only for true BMMs (shared_weight = False), where each batch item carries its own RHS. The old model charged batch everywhere: batch_penalty = b^1.4, multiplied into the entire score (wd_oldbaseline.py L997, L999). At b = 8 that is ×18.4 on compute, HBM, PSUM and tie-breaks alike.

That difference decides the canonical decode pick. A batch split is exactly how v3 rescues a tiny-M BMM: decode attn@V takes b = 8 to lift m_t from 2 to 16. Under the old multiplier that b = 8 inflated the whole estimate 18-fold and could never win. Under v3 it costs a flat 30 µs — dwarfed by the 90 µs of underfill it removes.

FIG · BATCH +30 µs vs ×18.4. A batch split that genuinely rescues a starved tile can pay for itself when it is added; it never can when it multiplies everything. wd_v3.py L1075-1077 · wd_oldbaseline.py L997
The principle Every guard rail is additive and one-sided: it charges for a measurable shortfall — too few rows, too few lanes, an over-wide N, too few cores, an unmerited batch split — and nothing once the tile is healthy. A toll that can only ever push toward a fuller array, never away from one, is why v3 breaks ties the way the hardware would.

§ 04 · SUPERSEDES 196d768

04 What it replaced

Physics v3 is the scorer now living in torch_spyre/_inductor/work_division.py on main. It displaced the model at commit 196d768 — a model that was rarely wrong about the hardware, but was wrong about how to combine what it knew. Three structural choices, each defensible in isolation, compounded into a cluster of bad decode and attention picks. This section takes each apart and names its v3 replacement.

All three share one symptom: the planner kept landing on the pure-M default 1·32·1·1 — 32 cores, every one of them fed only 2 token rows. It looked responsible. It starved the array.

Using all 32 cores looked responsible.

1 · One multiply governed everything

The old score was a product, not a sum:

score = (compute_us + hbm_us + psum_us + target_m_us) * batch_penalty
batch_penalty = b ** 1.4        # _BATCH_SPLIT_EXPONENT

The batch penalty did not sit beside the other costs — it scaled the entire estimate. Split a true BMM across b = 8 head-batches and every term, the useful compute_us and hbm_us included, was multiplied by 81.4 = 18.4×. Batch parallelism is exactly the lever decode attention needs when each item carries too little M; the old model made it look 18× more expensive than it is, and vetoed it by arithmetic.

v3 charges the same intent as one additive segment — batch_split_us = log2(b) * 10, true-BMM only. At b = 8 that is +30 µs appended to the ledger, not 18.4× multiplied through it.

196d768 — whole score × b^1.4 physics v3 — one appended batch_split segment
FIG 6·A The dial vs the addend. For the same b = 8, the old model multiplied the whole estimate by 8^1.4 = 18.4× — even the useful physics. v3 appends a single log2(8)·10 = 30 µs segment. An additive term is independently tunable; a multiplier reaches everything.

2 · PSUM was billed on the whole tensor

A K-split spreads one reduction across k cores; the partial sums cost k − 1 ring hops. The old model charged each hop against the entire output: 

psum_us = (k - 1) * (B * M * N) * 1.4e-4     # whole output, per hop

But a hop only touches the output tile a core actually owns — (B·M·N)/(b·m·n), not the full tensor. Billing the whole output made every K-split look ruinous, so reduction parallelism was left on the table even where it was the only way to fill the array.

v3 charges the per-core tile and separates the two operand regimes:

psum_us = (k - 1) * (B*M*N)/(b*m*n) * coeff
coeff   = 1e-3  (shared_weight)   |   1e-4  (true BMM)
Worked — decode QKT, k = 2 A legal one-stick K-split — decode QKT at 4·4·1·2, k = 2 landing a clean 64-element (one-stick) K tile per core — was billed against the whole B·M·N output by the old model: ≈165 µs of PSUM for a single ring hop. It never won. Under v3's per-core billing the same split is charged only (B·M·N)/(b·m·n) — b·m·n = 16 shrinks the tile 16-fold to ≈7 µs, cheap enough to pick.

3 · The hard trade-down guard

This is the single biggest source of the bad picks. After the cost function found its argmin, the old planner ran one last gate (work_division.py:1110): 

# Never trade down to fewer cores than the default distributor already found.
if math.prod(new_splits.values()) < math.prod(splits.values()):
    return splits          # -> the 32-core default: pure-M 1·32·1·1

If the cost minimum used fewer than 32 cores — which, for narrow decode shapes, it almost always did — the guard threw the answer away and returned the distributor's 32-core default: the pure-M 1·32·1·1. The cost function was allowed to be right, then overruled. Decode MLP-down is the clean autopsy: the device-best split is 1·4·4·1 (16 cores, 689 µs), but the guard forced 1·32·1·1 at 2043 µs — +197%. It is the leading driver of the bad-decode cluster — +197% on MLP-down, +169% on Q/O projection.

v3 deletes the wall and prices core count as a soft opportunity cost instead: 

core_underuse_us = log2(max_cores / cores_used) * 150     # _CORE_UNDERUSE_PENALTY_US

Dropping to 16 cores now costs a knowable 150·log2(32/16) = 150 µs — a discouragement, not a veto. When the healthier tile is worth far more than the fee (here a ~1350 µs saving), v3 takes it. The old wall could not.

v3 · core_underuse = 150·log2(32/cores) — a soft ramp 196d768 · trade-down guard — a hard veto wall forced pure-M landing · 1·32·1·1 · +197%

THE PAYOFF · REGIME-AWARE SHAPING

05The M-fill gate

One instinct runs through the whole model: spread work off a pure-M split so every core gets rows to stream over the stationary weight. That instinct wins decode, where M is tiny and pure-M starves the PT array — and it would lose prefill, where M already fills the array and extra splitting is only layout and fusion fallout. v3 reconciles the two with a single boolean.

Let m_t = M // m be the rows each core actually gets. The PT streams them in passes of _PT_ROWS = 8; the underfill target _M_TILE_UNDERFILL_TARGET = 16 is two full passes. From that one number v3 derives a latch:

filled_m_tile_factor = 1.0 if m_t >= 16 else 0.0

The factor arms the array-shape penalties. Below 16 rows/core the array is starved, the factor is 0, and the shape penalties vanish — the planner is free to do whatever it takes to feed the PT. At or above 16 the array is fed, the factor is 1, and the shape penalties switch on to stop gratuitous over-splitting. Same model, two regimes.

Penalize an awkward split only once M already fills the array. Starve the array, and every spread is fair game.

The latch arms large_m_tile_shape_us, a sum of three geometry-driven sub-terms. Two are gated by filled_m_tile_factor — they exist only to unwind over-splitting once the array is already fed. The third, the long-K down-projection guard, is ungated pure geometry.

Read the two lanes together and the "opposite instincts" collapse into one mechanism. The gate encodes no rule about attention or projections — only when the array is full enough to have an opinion about tile shape. Below the fill line, shape aesthetics are irrelevant; getting rows onto every core is all that matters. Above it, tile shape is the only thing left to get wrong.

DECODE attn@V · starved → spread

Old picks 1·32·1·1: all 32 cores, but m_t = 64/32 = 2. The gate is off, and m_tile_underfill = log2(16/2)·30 = 90 µs dominates — nothing resists moving off pure-M. v3 picks 8·4·1·1: m_t = 64/4 = 16, PT fed, underfill 0. The only added cost is batch_split = log2(8)·10 = +30 µs, additive — against the old model's multiplicative 8^1.4 = 18.4× on the entire score. Same 32 cores, a healthier per-core tile.

PREFILL attn@V · fed → kept

Here 1·32·1·1 already gives 512/32 = 16 rows/core, so filled_m_tile_factor = 1 and the gate is on. Because K = 512 ≫ N = 128, any N-split pays true_bmm_value_split = log2(512/128)·log2(n)·20 = 40·log2(n) µs — that is +40 µs even for n = 2. The value-guard makes every tiny-output split expensive, so v3 keeps the large-M tile untouched. Same instinct as decode, opposite regime.

Why the gate exists

An intermediate "first physics" model fixed decode but left prefill flat-to-slightly-worse in the block probe: with M already feeding the array, it still reshuffled large-M attention tiles (1·4·8·1 → 1·8·4·1) and inserted fresh N-splits (1·32·1·1 → 1·16·2·1). The gated shape terms exist to revert exactly those fed-regime over-splits while leaving the starved decode path untouched. One boolean, keyed to array fill, separates the regimes without a single op-name rule.

SYNTHESIS · THE CODE DIFF

07 What changed, and why it wins

Every change in physics v3 lives in one file — torch_spyre/_inductor/work_division.py — and not one line of it names Granite, attention, or SDPA. Seven edits turn a multiplicative guardrail that kept collapsing to all-32-cores pure-M into an additive datasheet that reads the per-core tile.

Two edits are structural. First, the score stops multiplying: the old model scaled its entire estimate by a batch dial b^1.4 — at b=8 that inflates every candidate by ≈18.4× — while v3 charges an additive log2(b)·10 instead, just +30 µs at b=8. Second, the old planner's hard trade-down guard (if prod(new)<prod(old): return default, L1110) forced the 32-core distributor split whenever the cost argmin wanted fewer cores; v3 swaps it for a soft core_underuse = 150·log2(32/cores) penalty, so a measured-good lower-core division can win on merit.

The rest make the physics honest. Shared-weight work — projections and MLP load one resident RHS across every token — must not be billed like a true per-batch BMM; edits #1, #2, #5 and #7 teach the score to tell them apart. And a family of shape-geometry terms (edit #6) gives the score the resolution to separate decode's starved small-M tiles from prefill's already-full large-M ones — all from observable shape, never an op name.

The seven edits, each traceable to a hunk in work_division.py:

Not one of these rows reads an op name. The score consumes only shape and hardware: B, M, N, K, whether the RHS is shared, cores used, per-core m_t = M/m and n_t = N/n, broadcast fanout, and the K-split PSUM cost. There is no "attention" branch and no "Granite" special case — those regimes fall out of the geometry.

The model in main now reads the tile, not the op name.

The payoff matches the 12-shape evidence exactly. The old model left several Granite matmuls on plainly bad divisions — decode projections and decode attention most of all, where the hard guard pinned pure-M 1·32·1·1 at m_t = 2. V3 moves those rows into fed split families and, in the same stroke, keeps the large-M prefill path from over-splitting an already-full array.
