# Granite fail-closed checkpoint - 2026-07-07

This checkpoint records the next Granite experiment after the bounded
flash/all-gather validation.  The key question was whether the latest
DLDSC gather/restickify path can safely remove all non-weight Granite HBM
spills, or whether some edges are too large and should remain HBM until WSR
tiles the region.

## What Changed In This Probe

Two local deltas were tested:

- `torch_failclosed_cap1m.diff`: lowers the default matmul-operand collective
  budget from 4 MiB to 1 MiB when `SPYRE_LX_PLANNER_RELAYOUT=1`.
- `deeptools_source_core_chunk.diff`: makes gather/restickify chunking consider
  source-core pressure as well as destination-core pressure.

These were diagnostic deltas.  The important result is not the exact cap value;
it is the boundary: full Granite activation relayouts must fail closed until WSR
can make the communication tile-scoped.

## Main Findings

1. Bounded substrate validation still holds.
   The focused Deeptools tests passed after the source-core chunking patch:
   `MatmulOperandBroadcast*` and `CoreWorkDivIncomptLxRelayout*`.

2. The full Granite first-projection activation is too large for the current
   full-materialization gather/restickify lowering.
   The failing edge is RMSNorm/mul output with producer split `{mb:32,out:1}`
   consumed by a matmul with `{mb:4,out:8,in:1}`.  This is an all-gather /
   replicate communication class over the full `B=1,S=512,E=4096` activation.

3. Deeptools lowering fails in two different ways depending on chunk size:
   default/smaller chunking either times out or eventually exceeds DCC IBUFF;
   larger chunking also exceeds IBUFF.  See
   `dxp_full_activation_replay_summary.md`.

4. With the 1 MiB frontend cap, Torch preserves the HBM fallback for this full
   activation.  The Granite run no longer hits the previous DXP relayout crash.
   It gets through compilation and fails later at runtime with:
   `convert_address not yet implemented - waiting for flex support`.
   That runtime issue is separate from the relayout planner decision.

5. The cap run emitted no backend relayout plans for this Granite case.  That is
   expected for the fail-closed policy, but it also means this particular run is
   not a performance proof of the attention/SwiGLU relayout wins.

## Interpretation

This supports the current scope boundary:

- The DLDSC communication substrate can represent and realize bounded
  scatter/broadcast/multicast/gather/all-gather tiles.
- Full Granite activation all-gather is valid as a communication class, but
  unsafe as a full-tensor materialization in the current backend lowering.
- WSR should own splitting this activation into smaller live tiles.  Once WSR
  presents bounded tiles, this substrate is the right place to realize the
  movement on chip.
