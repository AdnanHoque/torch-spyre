# Partial-View Gather Progress - 2026-07-07

## Summary

The remaining in-scope Granite activation HBM uses are not plain scatter edges.
The latest Granite S=512 one-gate artifacts show that explicit `ReStickifyOpHBM`
rows are weight-only, but two activation handoffs still use HBM/pool-backed
operands:

1. QKV projection output `buf6` into split Q/K/V attention consumers.
2. Fused MLP front projection output `buf33` into `silu` and `mul` split halves.

Both are **partial-view gather** problems: a producer owns a larger tensor, while
the consumer reads a slice/view of that tensor at a non-zero logical offset and
with a different core division.

## What Was Tried

A small Torch-side prototype adds Python-side `TensorArg` fields:

- `source_name`
- `source_offset_elems`

This is archived as:

```text
torch_partial_view_source_offset_qd_only.patch
```

The fields are currently emitted only in generated QD Python. This is safe for
frontend diagnosis and proves the contract can be recovered from the folded
load index.

## What Did Not Work

I tried emitting `sourceBufferName_` and `sourceOffsetElems_` into SDSC
`scheduleTree_` allocation nodes. That is **not viable without backend parser
support**:

- Putting those keys under `coordinates_` caused DXP to treat them like coordinate
  dimensions and crash with `std::out_of_range: map::at`.
- Moving them to allocation-node top level still crashed in the same first
  Granite bundle.
- The old and new first-bundle `sdsc_7.json` normalize to identical JSON once
  schedule-tree source fields are removed, so the QD-only prototype itself is
  not the source of the DXP crash.

This implies partial-view provenance should be carried through a backend-agreed
metadata contract, most likely `lxRelayoutClassifications_`, or Deeptools must
explicitly accept new allocation-node fields.

## Communication Class

This is a new class relative to PR1 scatter:

```text
partial_view_gather(source_buffer, source_offset, source_distribution,
                    consumer_distribution, consumer_view_shape)
```

It is copy-only, not arithmetic. It is not reduce/all-reduce. It differs from
plain scatter because the consumer does not read the whole producer tensor; it
reads a logical slice of a larger producer tensor.

## Frontend Requirements

Torch needs to:

1. Preserve or reconstruct the producer base buffer name after `split`/`getitem`
   have folded into `ReinterpretView` / index arithmetic.
2. Compute the constant element offset for each consumer view.
3. Attach producer core residency and consumer compute distribution to a stable
   relayout classification record.
4. Reserve destination LX workspace for the post-relayout consumer view.
5. Keep existing weight `ReStickifyOpHBM` rows out of scope.

## Backend Requirements

Deeptools needs to:

1. Accept the partial-view gather classification.
2. Use source buffer + source offset to compute source LX address ranges.
3. Materialize the consumer view in LX before the pointwise or matmul consumer.
4. Support the class for both pointwise consumers (`buf33 -> silu/mul`) and
   split Q/K/V attention consumers (`buf6 -> Q/K/V`).
5. Avoid requiring arbitrary unknown fields in `scheduleTree_`.

## Current Status

- Scatter/permutation: covered by PR1.
- Matmul operand gather/all-gather with `ReStickifyOpLx`: working in compile/DXP
  probes when the source is already LX.
- Explicit non-weight `ReStickifyOpHBM`: no remaining rows in the inspected
  Granite run; remaining explicit HBM restickifies are weights.
- Partial-view gather: identified as the next required class; frontend can
  recover source offsets; backend contract/realization remains to implement.
- Reduce/all-reduce: not proven as a current Granite spill blocker in this run.
