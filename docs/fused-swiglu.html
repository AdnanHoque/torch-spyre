Keeping SiLU in the registers

Fusing a matmul and its SiLU activation into one on-chip kernel — so the gate tensor is computed, activated, and consumed without ever touching memory.

Auto-fusing · device-validated · ah/fused-swiglu-prod @ f51346c

The shape of the problem: SwiGLU

Modern transformer MLPs use a gated feed-forward block. Granite-3-8B's is a SwiGLU: two parallel projections of the input, one of which is passed through a SiLU activation and used as a gate on the other.

out = down_proj( silu(gate_proj(x)) * up_proj(x) )

SiLU (a.k.a. swish) is silu(x) = x · sigmoid(x) — a smooth, self-gating activation. The interesting term for us is the highlighted one: a matmul immediately followed by an elementwise SiLU over its full output. That gate_proj(x) result — call it the gate tensor — is d_ff = 12,800 wide. It exists only to be activated and multiplied away. The question is where it lives while that happens.

The Spyre data path, and why "where" matters

A matmul on Spyre flows through a fixed pipeline of compute units, each with its own memory close by. The speed gap between those memories is enormous — and it is the entire story of this optimization.

The compute path itself is: the PE array (a systolic grid that does the multiply-accumulate) hands results to the SFP (a scalar/float unit that applies pointwise math over its LRF registers), which can spill to LX, which can spill to HBM.

PE → SFP → LX → HBM

The key fact: an output tile produced by the PE array is already sitting in the SFP/PE LRF registers. If you can apply SiLU to it right there, before it is written anywhere, the gate tensor never becomes a real buffer.

Three ways to fuse — and one that wins

There are three granularities at which you can run "matmul, then SiLU." They differ in how many device kernels launch and, crucially, in whether the d_ff-wide gate tensor gets materialized in LX.

OPTION 1

Matmul → decomposed SiLU

matmul
↓ write gate → LX
↑ read gate ← LX

leaky · default
OPTION 2

Matmul → single fused-SiLU op

matmul
↓ write gate → LX
↑ read gate ← LX
silu (one op)
2 segments. Gate still written + read on LX. SiLU is one op, not six.
stepping stone
OPTION 3 — BUILT

Matmul with SiLU in the epilogue

matmul → tile in LRF
silu on tile (in-register)
✗ gate never materialized
write activated result
1 segment. Tile stays in the SFP LRF across the matmul→silu boundary. The gate tensor is never a buffer.
this work

Why 3 wins is exact, not hand-wavy. Options 1 and 2 both force the full gate tensor out to LX and back — one write and one read of a 12,800-wide tensor — plus a second kernel launch to read it. Option 3 applies SiLU to each output tile while it is still in the SFP LRF, then writes only the finished result. The structural saving is guaranteed: −1 device segment, −1 LX write, −1 LX read of the gate tensor.

How the SiLU is computed in-register (FEST)

Applying SiLU inside the matmul kernel means computing sigmoid(x)·x using only the units that already hold the tile. Sigmoid is the hard part — so we lean on the PE array's FEST unit (Fast Exponential / Sigmoid Transcendental), which produces a piecewise-linear fast-sigmoid as a slope + offset pair, then finish with a couple of SFP fused-multiply-adds. No transcendental library call, no memory spill.

The recipe, all in registers, folded into the matmul's final accumulation iteration:

PE FEST mode 7
→ cs (fast-sigmoid offset / curve term), reading the fp16 matmul result still in PE LRF
PE FEST mode 6
→ ss (fast-sigmoid slope term), same input
SFP FMA16
t = cs·1.0 + 0.5 — the +0.5 is a staged fp16 constant 0x3c00
SFP FMA16
sig = x·ss + t → the fast-sigmoid value
SFP FMUL
out = sig · x, written in place — this is the SiLU result

This lives in bmm.ddl as a new %silu_op guarded by ddl.if(%silu_op), mutually exclusive with the relu / bias / batchnorm epilogues (a v1 register-pressure guard). The PE-side FEST outputs get PE-LRF allocations so the 128-wide FEST path resolves.

Making the compiler fuse it automatically

The device kernel is only half the work; Inductor has to recognize the pattern and emit one fused segment. A real vertical-fusion gate in scheduler.py — can_fuse_matmul_silu — fires when three things hold:

matmul node
a reduction whose type is batchmatmul
silu node
a pointwise node whose origins target aten.silu
full consume
the SiLU's only non-constant read is the matmul output, and its numel matches (no broadcast, unary)

When it fires, the two ops collapse into one FusedSchedulerNode (sdsc_fused_mm_silu_0), and the SDSC codegen emits a length-2 computeOp_ vector via an Epilogue record threaded through superdsc.py → bundle.py → compute_ops.py:

batchmatmul+silu exUnits [pt, sfp] · one segment

A plain a @ b still emits a length-1 computeOp_ = [batchmatmul] — the change is behavior-preserving. The whole thing is default-on (SPYRE_ENABLE_MATMUL_SILU_EPILOGUE=1); setting it to 0 restores the two-op path, which is exactly the benchmark control.

No forced hook. The prototype used an SPYRE_EXP_FORCE_MM_SILU env switch. That is gone. Production fusion is driven entirely by the detection gate above.

The fusion demonstrably engages on device — the SDSC segment vector changes, identically for prefill and decode:

BASELINE bmmsilubmmmulbmm
FUSED    bmm+silubmmmulbmm standalone silu eliminated

Honest read. The plumbing is correct end-to-end and the structural win (one fewer segment, no LX round-trip of the gate) is real — but at Granite batch=1 the payoff is small: ~1% on prefill, noise on decode. That is expected. Three large 4096×12800 matmuls dominate the block, and the eliminated SiLU is a cheap elementwise op over a modest tensor; the saved LX round-trip and launch is tiny against that. The fusion pays off more where the activated tensor is large relative to the matmul, or where launch overhead is a bigger fraction of the total — not this shape.

Caveats. v1 is unary-SiLU only and mutually exclusive with other epilogues (enforced in both the DDL and the frontend). HPM / bandwidth counters were not captured — the perf-suite profiler hung and was abandoned for the lighter probe; wall-clock only. Kept local, not pushed, per pre-publish convention.
