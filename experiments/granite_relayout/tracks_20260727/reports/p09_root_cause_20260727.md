# Why P09 does not fire, and what fixing it actually requires

Date: 2026-07-27

P09 relayouts the normalized activation into the Q/K/V projection matmuls. It works in
isolation and does nothing in the accepted stack. This is the chain, established by
instrumenting the merged tree at `/home/adnan/claude-isolated/p07_integrated_20260727`
and running one-iteration full-model compiles at `DXP_LX_FRAC_AVAIL=0.2` (production
value; not varied).

## What the failure looks like from outside

```
buf10   address=null  size=0
        reject_reason = "core div mismatch: broadcast read on 'buf11':
                         view covers 8 cores but op runs 32"
```

The run still generates token 203. That is the silent-drop pattern: the edge is
abandoned and the model computes correctly without it, so correctness proves nothing
here.

## Three things were wrong. Only the third is the real blocker.

### 1. Grouped-query attention was ignored (real bug, fixed)

```python
if is_prefill_qkv_input and shape == ["1", "512", "4096"]:
    return {"mb": 16} if name == "buf10" else {"mb": 8, "out": 4}
```

Instrumenting the four buffers this rule is meant to cover:

| buffer | role | shape | matched |
| --- | --- | --- | --- |
| buf10 | normalized activation | `[1,512,4096]` | yes |
| buf11 | Q projection | `[1,512,4096]` | yes |
| buf15 | K projection | `[1,512,1024]` | **no** |
| buf29 | V projection | `[1,512,1024]` | **no** |

Granite is grouped-query: 32 query heads but only 8 KV heads, so K and V are
8 x 128 = 1024 wide while Q is 32 x 128 = 4096. Hard-coding 4096 silently skipped
two of the three consumers. Fixed by accepting both widths. Note the neighbouring
`is_output_projection` rule already accepts two shapes for the same tensor, so this
was an inconsistency within the file, not a new idea.

### 2. The edge gave up when the producer was not on 16 cores (relaxed)

```python
if oracle_qkv_input_edge:
    if (producer_core_count != 16 or ...):
        continue
```

In isolation the activation is deliberately placed on 16 token owners. In the accepted
stack it is on the 8-token x 4-hidden 32-core grid. The predicate abandoned the edge
rather than planning a gather from that layout -- even though P03 gathers from exactly
that layout for the gate/up matmuls. Changed to fall through instead of `continue`.

### 3. The buffer names do not denote the intended tensors (the actual blocker)

Neither fix changes the outcome: same 3 relayout plans, same 9 shuffles, same
rejection. Instrumenting the edge walk shows why:

```
P09DIAG3  buf10 -> consumer=buf8   read_count=1   gate_ok=False
```

P09 expects `buf10` to be read three times, by `buf11`, `buf15` and `buf29`. In the
accepted stack `buf10` has **one** consumer, `buf8`. It is not the normalized
activation. Every P09 predicate keys on these literal names, so none of them match
anything, and no plan is ever produced.

The name is not a stable identifier. Buffer numbering is assigned during lowering, and
the accepted stack's other oracles insert and fuse ops -- visible directly in the op
sequence, where the accepted stack has `6_shuffle` and `7_identity` before ops that the
isolated graph numbers differently:

```
isolated:  ... 7_mul  8_mul  9_shuffle  10_batchmatmul 11_mul 12_sumnonstick ...
accepted:  ... 6_shuffle 7_identity 7_mul 8_mul 8_shuffle 9_batchmatmul 10_mul ...
```

This is the same root cause as P07, which also compiles, is also token-correct at full
scale, and also never fires because its matcher keys on `buf12`/`buf16` plus an exact
shape from its isolated configuration.

## What fixing P09 requires

Not a patch to the predicates -- a change of addressing scheme. The edge must be
identified by structure rather than by name:

> the rank-3 `[1, 512, H]` output of the pre-attention RMSNorm, read by three
> batch-matmul consumers whose output widths are `H`, `H/4`, `H/4`

That description is stable under renumbering and already encodes the grouped-query
asymmetry. The same treatment fixes P07 and would immunise every remaining edge against
the next graph change, which is worth more than either edge individually: **six of the
numbered edges currently key on literal buffer names**, so any of them can silently stop
firing whenever the surrounding stack changes, while continuing to pass the token gate.

Until then the honest status of P09 is: correct, inert, and worth ~0 ms.
