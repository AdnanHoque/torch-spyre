## The rebase

Base moved `b4ae70f` â `2c832809`, seven upstream commits. Only one of them looks dangerous, and it looks *very* dangerous: **d82fe886 reverts #3615**, and the old base `b4ae70f` **was** #3615. So this branch was literally sitting on the commit that has now been reverted.

**What the revert removed.** 22 lines from `torch_spyre/_inductor/patches.py` that popped four keys out of `torch._inductor.fx_passes.post_grad.noop_registry` for the duration of `enable_spyre_context`: `aten.copy.default`, `aten.clone.default`, `aten.clone.out`, `aten.alias.default` â plus 102 lines of tests. Note the op set: it is **clone**, not just copy. That matters, because the SHUFFLE this feature inserts *is* a clone â `graph_editor.py:147-149` creates the FX node with target `self.clone_aten_op`, resolved at `graph_editor.py:45-49` by scanning inductor's `lowerings` for the entry whose lowering is `clone_lowering`. So the naive framing ("it's a copy, the revert was about copies") is wrong. The right framing is: same op family, and here is why it is still safe.

**Reason 1 â ordering, and this one is decisive.** `noop_registry` has exactly one consumer, `remove_noop_ops`, invoked at `torch/_inductor/fx_passes/post_grad.py:170` inside `post_grad_passes`, reached from `compile_fx.py:1344` â i.e. on the post-grad **FX graph, before `GraphLowering.run()`**. The relayout copy is created by `materialize_lx_relayouts`, the last statement of `_push_allocation` (`scratchpad/allocator.py:1016`), which is the last entry of `CustomPreSchedulingPasses` (`passes.py:464`), driven by the `_update_scheduler` monkeypatch (`patches.py:113-122`), which torch calls from `GraphLowering.codegen()` (`graph.py:2437`). The pass that could delete the copy has finished hundreds of steps before the copy exists. There is no re-entry: nothing re-runs `post_grad_passes` on the module after lowering. The reverted code's own comment says it â these ops are discarded *"before it reaches lowering"* â and all four deleted regression tests (`test_copy_not_deleted`, `test_clone_not_deleted`, â¦) exercise clone/copy the **user** wrote into the traced program.

**Reason 2 â packet vs. overload.** Verified by execution, not by reading. In torch 2.11, `[k for k,v in lowerings.items() if v == clone_lowering]` returns `[OpOverloadPacket(aten.clone), OpOverload(aten.clone.default), OpOverload(aten.clone.out)]` â packet first, per `get_overloads` (`lowering.py:322-335`) plus `dict.fromkeys` (`lowering.py:524`). GraphEditor's `break` therefore binds `clone_aten_op` to the **packet**. And `torch.ops.aten.clone in noop_registry` is `False` while `torch.ops.aten.clone.default in noop_registry` is `True`: `_add_op_to_registry` (`torch/_decomp/__init__.py:64-91`) expands packets and only ever stores `OpOverload` keys. `node.target in noop_registry` is False even in the hypothetical where the pass could see the node.

**Reason 3 â no `meta["val"]`.** `same_meta` (`post_grad.py:993-1011`) returns False unless both nodes carry `meta["val"]`, and `Graph.create_node` does not populate it.

**The only post-materialization deleter, and why it can't produce the bad shape.** The one pass that can delete the copy *operation* after materialization is `Scheduler.dead_node_elimination` (`torch/_inductor/scheduler.py:3528`, called at `:2953`), which runs before `_pre_fusion_custom_pass` (`:2966`) and `_post_fusion_custom_pass` (`:2977`). It drops a node only when every user of every output buffer is weak or already removed (`:3541-3553`). `_replace_loop_input` (`graph_editor.py:265-275`) rewrites the consumer's `inner_fn` to load the clone and calls `invalidate_op_read_writes`, so by the time `compute_dependencies` runs the consumer names the clone, not the source. Deleting the copy therefore requires deleting the consumer â the dangerous shape (copy gone, consumer still reading the source under the source's ownership map) is not constructible. Spyre's own `remove_kernel_local_buffers` (`spyre_kernel.py:973-983`) and the `V.graph.removed_buffers.add(...)` sites do run past the backstop, but they drop buffers from the **kernel arg list**, which is normal handling for every LX buffer; the OpSpec and its per-core divisions still reach the emitter.

**And if a copy ever did vanish, the feature detects it.** `scheduler.py:502-504`: any plan whose copy is absent from the schedule is registered as `missing relayout copy {copy_name}` â `demote()` â `clear_lx_state` (`lx_relayout.py:117-121`) pops `allocation["lx"]` and nulls `lx_view` for the whole group. That runs in `_post_fusion_custom_pass`, strictly after DCE and immediately before `hbm_pool_planning` (`passes.py:284-290`), so the source lands in the HBM intermediates segment: slower, not wrong. The PR never assumes the copy survives.

Corroborating: `push_allocation_with_clone` already ships on main (`2c832809 allocator.py:838/844`) under the already-reverted state. If the revert broke this mechanism, main would already be broken.

**The rest of the seven commits.** Of the six others, only `4c471e27` (depthwise-conv2d) interleaves with this PR at all. It cannot be a relayout consumer: `DEPTHWISE_CONV2D_OP` is not in `MATMUL_REDUCTION_OPS` (`constants.py:23`), and a conv2d `ComputedBuffer`'s `.data` is a `Reduction`, not `Pointwise`, so it breaks the consumer loop at `lx_relayout.py:297`. It also cannot be perturbed by this PR: `spyre_kernel.py:955-958` nulls `work_division` and `lx_consumer_is_matmul` on every arg of any OpSpec for which `is_lx_relayout_identity` (`op_spec.py:203-215`) is False, so `compute_ops._tensor_core_map` still returns `{}` for conv and `coreIdToWkSlice_` is unchanged. The one place the two changesets actually touch is `superdsc.py:1187-1191`, a hand-resolved conflict where `MATMUL_LAYOUT_LABELS if not use_op_dims else LAYOUT_LABELS` became `_get_tensor_layout_labels(use_op_dims, op_spec.op)` â the helper 4c471e27 introduced, which adds a `CONV2D_LAYOUT_LABELS` arm. For the SHUFFLE identity, `use_op_dims = not _is_matmul(op) and not _is_conv(op)` is True, so both forms return `LAYOUT_LABELS` and the conv arm is unreachable. Correct, but it is the one line in this rebase that deserves a second pair of eyes.

`bb8218cd` (label vocabulary) is satisfied: `tests/configs/torch_spyre_tests/inductor/test_work_division_hint_config.yaml` already declares `labels: [unit, regression, integration, trunk]` at `2c832809` and the PR doesn't touch it; `unlisted_test_mode: mandatory_success` auto-discovers the 367 new test lines. `0c45a303` deletes one C++ header, zero Python surface. `706978d3` is the docs commit â see below.

**On the `patches.py` idempotence guard.** It is consistent with the earlier deletion of the ~44-line registry replay, and it is not a rebase artifact: `git diff cc90711b cd6b0005` shows the guard added and the replay cluster removed **in the same commit**. Two halves of one change â the replay made a second pipeline run survivable, the guard makes the second run not happen. The double-run is real and exercised: `test_lx_relayout_two_private_consumers_are_numerically_correct` (`tests/inductor/test_work_division_hint.py:675`) passes `options={"epilogue_fusion": False}`, which makes `config_patches` non-empty, so upstream `compile_fx` self-recurses through the patched module global (`torch_spyre/_inductor/__init__.py:156`) and `enable_spyre_context` nests.
